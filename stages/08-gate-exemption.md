# ステップ 8: 除外された命令の悪用

- **元の攻撃**: `attacks/09_gate_exemption_chain/`（演習 2.8）
- **所要時間の目安**: 25〜35 分
- **前提**: ステップ 6・7（位置を地上局の範囲内にすることと、地上局モードを有効にすること）
- **画面のスコアボード**: `DEBUG ON`（USB デバッグが実際にオンの間、点く。状態を表す項目）

## ねらい

「例外として通す命令」が攻撃の入口になることを知り、**スクリプトの結果をそのまま信じずに、コードで確かめる**練習をする。

## 背景

ステップ 7 では、地上局モードを有効にすると、認証されていない相手の命令がゲートで拒否されました。
ただし、ゲートにはわざと通す命令（除外）があります。衛星が不調になったときでも調べられるよう、デバッグの設定を変える命令 `DEBUG_CONFIG` は、ゲートを素通りします。
1 つ 1 つは理由のある設計です。では、これらを組み合わせると、何が起きるでしょうか。

## 注意

- このステップの元のスクリプトは、このファームウェアでは**そのままでは最後まで成功しません**。JP-Bootcamp の資料（`docs/04-attacks.md` の「キット自体の2つの欠陥」）にも、そう書かれています。
- 失敗するのは正しい結果です。なぜ失敗するかを確かめ、直すのが、このステップの B です。
- 終わったら、必ずリセットしてください。USB デバッグがオンのまま残ると、次のステップが失敗します。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: ゲートが有効なとき、`DEBUG_CONFIG` で USB デバッグをオンにすると、ほかの命令の扱いは変わると思う？
- Q2: USB デバッグがオンの間、衛星は暗号化された命令をどう扱うと思う？
- Q3: センサー（IDS）は「デバッグをオンにする」と「ゲートを切る」の、どちらに気付くと思う？ 両方？ 組み合わせ？

## 操作

### A. 用意されたスクリプトで試す

1. このステップを始める前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
   ステップ 7 で開いた地上局のセッションが残っていると、ゲートが最初から開いていて、比べられない。
2. 位置を札幌にし、地上局モードを有効にする。このリポジトリの `attacks/` で、次を順に実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python 03_gps_spoofing/03_gps_spoofing_usb.py --lat 43.0618 --lon 141.3545
       FLATSAT_HOST=1 uv run python ../tools/gs_mode_on.py

   画面に `GS ON` が出て、`GS AUTH` は出ていないことを確かめる（ゲートは有効、セッションはない）。
3. ゲートの除外を悪用する攻撃を試す。

       FLATSAT_HOST=1 uv run python 09_gate_exemption_chain/09_gate_exemption_chain_usb.py

4. 出力を、`===` の見出しごとに区切って、上から読む。**次の見出しへ進む前に、その区切りの問いに答える。**

   - `=== 0. baseline: is the gate even on? ===`
     - 下に出る英語は「地上局モードがオフなら、この演習では何も起きない。先にオンにする」という注意。手順 2 で済んでいる。
   - `=== 1. an ordinary command, with the gate up ===`（ゲートが有効なまま、スラスターの命令を送る）
     - `[=]` の行は `refused`（拒否）と `ACCEPTED`（受け付け）のどちらだったか。
   - `=== 2. the exempt command. The gate never refuses this one ===`（除外の命令で、USB デバッグをオンにする）
     - 画面のスコアボードの `DEBUG ON` は点いたか。
   - `=== 3. with debug on, the gate can be switched off from USB ===`（ゲートを切る命令を送る）
     - `[<]` の行に `ERROR` は返ってきたか。返ってきたなら、ゲートは切れたと言えるか。
     - 次の区切りを読む前に、手順 1 と同じ命令がどうなるかを予想する。
   - `=== 4. the same command as step 1, unchanged ===`
     - `[=]` の行は 1 と比べて変わったか。
   - 最後の `[+]` または `[?]` の行を読む。`[?] no clean before/after` と出た場合、スクリプトは「たぶん地上局モードが最初からオフだった」と推測している。**手順 2 で確かめたことと、この推測は合っているか。**
5. ボードの画面を見る。`GS ON` は消えたか、残っているか。

### B. 自分で組み立てる

6. A の結果がスクリプトの推測と合わない理由を、コードで確かめる。`Firmware/worker.cpp` の `secureLinkDecodeInPlace` を読み、USB デバッグがオンのとき、暗号化された命令がどう扱われるかを調べる。手順 3 の命令（`GS_MODE` に `00`）は、暗号化されて送られている。ボードはどのバイトを `00` と比べることになるか。
7. スクリプトを同じフォルダにコピーし（たとえば `my_09.py`）、手順 3 の命令を**暗号化しないで**送るように変える（`fsat.send` には `encrypt=False` を渡せる）。リセットから手順 2 までをやり直してから実行し、結果が `[+] refused, then accepted.` に変わるか確かめる。
8. 手順 7 で `ACCEPTED` になったスラスターの命令が、本当にスラスター 1 を出力 `0x40` にしたかを、コードと Python で確かめる。手順 4 の命令も暗号化されて送られている。ボードがそれを復号しないなら、先頭のバイト（スラスターの番号として読まれる）は何になるか。`attacks/` で次を実行して求める。

       uv run python -c "import sys; sys.path.insert(0, 'lib'); from flatsat import encrypt_payload; print(hex(encrypt_payload(bytes([1, 0x40]))[0]))"

   出た番号を、`worker.cpp` の `commandApidHandler` の `SPP_APID_TC_SET_THRUSTER` の分岐に当てはめると、どの処理に進むか。狙いどおりにならないなら、手順 4 の命令にも `encrypt=False` を足す。
9. 終わったら、**リセットする**。

## 観察しよう

- ボードの返事: 元のスクリプトの手順 3 に、`ERROR` は返ってきましたか？ 直したあとはどうでしたか？
- スクリプトの判定: 元のスクリプトの `[?]` の推測は実際の原因と合っていましたか？
- ボードの画面: `DEBUG ON` はどの時点で点きましたか？ `GS ON` はどの時点で消えましたか？
- スラスターの命令（B の 8）: `ACCEPTED` と表示されたとき、ボードはその命令をスラスターの何番への命令として読みましたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 元のスクリプトのときと、直したあとで、出たアラートは違いましたか？

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点 1: 除外の命令が、ゲートを切れる状態を作る**: ゲート（`Firmware/worker.cpp` の `groundStationCommandAllowed`）は、`DEBUG_CONFIG` を無条件で通します。さらに、USB デバッグがオンなら、USB から来た「地上局モードを切る」命令も通します。地上局モードを切る処理（`commandGroundStationModeHandler`）にも、同じ「USB デバッグがオンなら切ってよい」という条件があります。除外の命令で状態を作り、その状態を使ってゲートそのものを切る、という 2 段の連鎖です。
- **弱点 2: USB デバッグがオンだと、暗号を使わなくなる**: USB デバッグがオンの間、ボードは USB から来た命令を復号しません（`secureLinkDecodeInPlace`）。返事も暗号化しません。デバッグのための例外が暗号まで外しています。
- **元のスクリプトが失敗する理由**: スクリプトは USB デバッグをオンにした直後の命令も暗号化して送っています。ボードは復号しないので、暗号文の先頭のバイトを `00` と比べます。このバイトが `00` になることはまれなので、「ゲートを切る」命令とは見なされず、ゲートに拒否されます（B の 6・7 で確かめたこと）。手順 4 のスラスターの命令も暗号文のまま「スラスターの番号」と「出力」として読まれるため、受け付けられても狙った値にはなりません（B の 8）。
- **スクリプトの推測を信じない**: スクリプトはうまくいかなかった理由を「地上局モードが最初からオフだった」と推測しました。実際の原因は別でした。スクリプトや AI の説明はもっともらしくても外れることがあります。「自分で確認できたこと」と分けて記録する理由がここにあります。
- **センサーの見方**: センサーには、`DEBUG_CONFIG` のすぐあとに地上局モードが切られたことを検知するルール（PWN-6 `gate-exemption-chain`）があります。どちらか 1 つだけなら日常の操作でもありえます。**2 つの組み合わせ**が問題だ、という考え方です。
- **教訓**: 例外のリスト（除外）は、それ自体が攻撃の入口になります。例外を足すときは、その例外で**何ができる状態になるか**まで確かめる必要があります。

## 直し方

考えてみてください。

- USB デバッグがオンでも、ゲートを切れないようにする。`groundStationCommandAllowed` と `commandGroundStationModeHandler` の**両方**にある「USB デバッグがオンなら」の条件を見直す。片方だけ直すと、もう片方から切れることがある。
- `DEBUG_CONFIG` をゲートの除外から外し、地上局として認証された相手からしか受け付けないようにする。
- USB デバッグがオンでも、暗号を外さない。
- 直したあと、直したスクリプト（B の 7・8）を実行し、**ゲートが切れないこと**と、スラスターの命令が拒否されたままであることを、実機で確かめる。

## ヒント

1. 手順 3 の命令は、ボードにどんなバイト列として届いていますか？ ボードはそれを復号していますか？
2. `worker.cpp` の `secureLinkDecodeInPlace` の、`usbDebugEnabled` を調べている行を読んでみてください。次に、`groundStationCommandAllowed` で、`gs_disable_request` が真になる条件を読んでみてください。
3. USB デバッグがオンの間は、暗号化しないで送る必要があります。手順 3 の `fsat.send(TC_GS_MODE, b"\x00", ...)` に `encrypt=False` を足すと、ゲートが切れます。手順 4 のスラスターの命令にも足すと、狙った値になります。
