# 段階 4: 位置のなりすまし

- **元の攻撃**: `attacks/03_gps_spoofing/`（演習 2.3）
- **所要時間の目安**: 15〜20 分
- **画面のスコアボード**: 専用なし（ステータス画面の位置と `OVR` バッジを見る）

## ねらい

位置情報のように、**誰も確かめていない入力を、権限の判断に使う**と何が起きるかを知る。

## 背景

この衛星は、地上局（衛星と交信する地上の基地）と「ハンドシェイク」（本人確認のやり取り）を始める前に、**自分が地上局の近くにいるか**を GPS の位置で確かめます。地上局は札幌にあり、半径 35 km の内側にいるときだけ、ハンドシェイクを始めます。
ボードの初期位置は東京で、地上局から約 830 km 離れています。では、衛星が信じている位置を、外から書き換えられたらどうなるでしょうか。

この段階は、次の段階 5 の**前提**になります。

## 注意

- この演習は、USB 経由で位置を指定する模擬のものです（講座用ビルドだけにある命令 `GPS_OVERRIDE`、番号 `0x14`）。本物の攻撃は GPS の電波を偽装しますが、**この演習では電波を一切扱いません。**
- 段階の最後に、位置は偽装されたまま残ります。次の段階 5 に続けて進む場合はそのままにし、進まない場合はリセットしてください。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 東京にいる状態で地上局とのハンドシェイクを始めようとすると、衛星は何と返事をすると思う？
- Q2: 衛星は、外から届いた位置が「本物の GPS の位置」かどうかを、見分けられると思う？
- Q3: 東京から札幌へ一瞬で移動したら、センサー（IDS）は気付くと思う？

## 操作

### A. 用意されたスクリプトで試す

1. 段階の前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
   起動時もリセット後も、位置は「東京への上書き」として設定されるため、最初から画面に `OVR` が出ている。
2. ボードの画面で、現在の位置を**メモする**。
3. ハンドシェイクを始められるかを確かめる。このリポジトリの `attacks/` で、次を実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python - <<'PY'
       import sys; sys.path.insert(0, 'lib')
       from flatsat import FlatSat, TC_GS_ACCESS
       with FlatSat(verbose=False) as f:
           for p in f.send(TC_GS_ACCESS, b"\x00", seq=1, listen=1.5):
               body = f.plaintext(p)
               if p.apid == 0x09:
                   print("ERROR:", body.split(b"\x00", 1)[0].decode("ascii", "replace"))
               elif p.apid == TC_GS_ACCESS:
                   print("GS_ACCESS reply:", body.hex())
       PY

   返事（`ERROR:` の文字列と、`GS_ACCESS reply:` の 16 進数）を**メモする**。
4. 位置を札幌（地上局の位置）に書き換える。

       FLATSAT_HOST=1 uv run python 03_gps_spoofing/03_gps_spoofing_usb.py --lat 43.0618 --lon 141.3545

5. 画面の位置と `OVR` バッジを確かめる。
6. 手順 3 を、もう一度実行する。返事は変わったか。

### B. 自分で組み立てる

7. 地上局の半径（35 km）の**境目**を、自分で確かめたい。`--lat` を少しずつ北へずらし（緯度 1 度は約 111 km）、手順 3 の返事が変わる位置を探す。何回目で境目を見つけたか、記録する。
8. 段階 5 に続けて進むなら、最後に札幌（手順 4）へ戻しておく。進まないなら、リセットする。

## 観察しよう

- ボードの返事: 東京のときと札幌のときで、手順 3 の返事はどう違いましたか？ 拒否の理由は何でしたか？
- ボードの画面: 位置の表示は、どう変わりましたか？ `OVR` バッジは、書き換えの前後で区別の手がかりになりましたか？
- 境目（B）: 半径 35 km の境目は、ほぼ計算どおりでしたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、位置が飛んだことを示すアラートは出ましたか？ 出なかったなら、なぜだと思いますか？

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点**: ハンドシェイクを始めてよいかを、**GPS の位置だけ**で決めています。位置は、誰も認証していない入力です。衛星は、届いた位置が本物の GPS から来たのか、偽物なのかを区別しません。
- **確認の順番**: この衛星の地上局ゲートは、**① GPS の位置が有効か → ② 地上局の範囲内か → ③ 認証済みか** の順に確かめます（`Firmware/worker.cpp` の `groundStationCommandAllowed`）。拒否の理由も `GS GPS INVALID` → `GS RANGE LOCK` → `GS AUTH REQUIRED` と変わります。位置をごまかすだけで、①と②は通れます。残る③が、段階 5 の主題です。
- **`OVR` バッジは手がかりにならない**: この演習のボードは、起動時の東京の位置も「上書き」として持っているため、`OVR` は最初から出ています。正規の位置も偽の位置も、衛星から見れば同じ「上書きされた位置」です。本物の GPS 偽装では、こうした印すら出ません。
- **センサーが気付けない理由**: センサーには、ありえない速さで位置が動いたことを検知するルール（UCEB-8 `position-jump`）があります。ただし、位置のテレメトリは暗号化されているため、センサーはセキュアリンクが**オフ**のときしか位置を読めません。暗号は、攻撃者だけでなく、**守る側の監視からも中身を隠す**ことがあります。
- **現実の例**: GPS の電波を偽装して、船舶やドローンの位置を狂わせる事例が報告されています。位置は「便利な判断材料」ですが、それだけで権限を決めると、位置をごまかすことが権限を得ることになります。

## 直し方

考えてみてください。

- 位置**だけ**で権限を決めない。位置は「追加の条件」にとどめ、本人確認（認証）を必ず別に行う。
- 位置の**もっともらしさ**を確かめる。たとえば、前回の位置から、ありえない速さで動いていないか。
- 位置の出どころを確かめる。講座用の `GPS_OVERRIDE` のような、外から位置を書き換える経路は、運用するファームウェアには入れない。
- ファームウェアでは、`worker.cpp` の `groundStationWithinRange` と、ハンドシェイクを処理する `commandGroundStationAccessHandler` を読んでみる。
- 直したあと、同じスクリプトで位置を飛ばし、**ハンドシェイクが始まらないこと**を、実機で確かめる。

## ヒント
