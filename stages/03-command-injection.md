# 段階 3: 認証のないコマンド

- **元の攻撃**: `attacks/02_command_injection/`（演習 2.2）
- **所要時間の目安**: 15〜20 分
- **画面のスコアボード**: `THRUSTER`（命令が**届いた**時点で点く。値が変わったかどうかは別に確かめる）

## ねらい

命令を受け取る側が、**送り主が誰かを確認していない**と何が起きるかを、実機で体験する。

## 背景

衛星の姿勢や軌道は、スラスター（小さな噴射装置）で変えます。スラスターを動かす命令は、衛星にとって特に重要な命令です。
この衛星への命令は、段階 2 で見たとおり暗号化されています。では、**正規の地上局ではない誰か**が、スラスターの命令を送ったらどうなるでしょうか。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 地上局ではない PC から、スラスターの出力を変える命令を送ると、衛星は受け付ける？ 拒否する？
- Q2: 受け付けたとして、衛星は「受け付けました」と返事をすると思う？
- Q3: 出力に、ふつうはありえない大きな値（たとえば 255）を指定したら、どうなると思う？

## 操作

1. 段階の前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
### A. 用意されたスクリプトで試す

2. このリポジトリの `attacks/` で、次を実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python 02_command_injection/02_command_injection_usb.py

   スクリプトは、変更前の値を読む → スラスター 0 の出力を 200 にする命令を送る → 変更後の値を読む、の順に進む。
   値は約 14 秒ごとに届くテレメトリ（`SEND_TM`）から読むため、**最大 35 秒ほど待つ**ことがある。止まったように見えても待つ。
3. 表示された「変更前」と「変更後」の値を**メモする**。
4. `--thruster-id`（0 か 1）と `--power`（0〜255）を変えて、何回か試す。たとえば `--thruster-id 1 --power 255`。

### B. 自分で組み立てる

5. スクリプトの `--thruster-id` は、0 と 1 しか受け付けない。**存在しない番号 2** を送ると衛星がどう反応するかを確かめたい。スクリプトのどこを変えればよいか、自分で読んで変える（AI に頼む場合も、変更点を自分で説明できるようにする）。
6. 終わったら、`--restore` を付けて実行する。`--restore` は、元の値ではなく**出力 0** に戻す（`--thruster-id` で指定したスラスターだけ）。リセット用のスクリプト（`reset_bench.py`）はスラスターを戻さないので、両方まとめて戻すなら USB ケーブルを抜き挿しする。

## 観察しよう

- ボードの返事: 命令を送った直後に、何か返ってきましたか？
- スラスターの値: 自分が送った値と、同じになりましたか？ 255 や、存在しない番号 2 ではどうでしたか？
- ボードの画面: `LAST CMD` に `THRUSTER` が出ましたか？ スコアボードの `THRUSTER` は、どの時点で点きましたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 出たなら、どのルールですか？ ルール名から、センサーが**何を問題にしたか**を考えてください。

スラスターの値は、約 14 秒ごとのテレメトリ（`SEND_TM`）のほか、衛星の状態（`STATUS`）の返事にも入っています。

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点**: スラスターの命令を受け取る処理は、**送り主が誰か**を確認しません。形の正しい命令が届けば、そのまま出力を書き換えます。
- **暗号があっても防げない理由**: 段階 2 で見たとおり、この衛星の暗号は、ファームウェアに書かれた**固定の鍵**を使います。鍵は公開されているソースコードに含まれるので、攻撃側のスクリプトも同じ鍵で暗号化できます。鍵をみんなが知っていると、暗号は「送り主の確認」の役に立ちません。
- **返事がない**: この命令は、受け付けても返事（ACK）を返しません。送った側は、成功したかを `STATUS` で別に確かめる必要があります。運用者から見ると、**誰かが勝手に変えても気付きにくい**ということです。
- **値の確認がない**: 出力は 0〜255 のどの値でも、そのまま受け付けます。存在しない番号を指定すると、ボードの内部ログにエラーが出るだけで、送り主には何も返りません。
- **スコアボードの意味**: `THRUSTER` は「命令が届いた」ことを示すだけです。出力が実際に変わったかは、テレメトリの値で判断します。
- **センサーが問題にしたこと**: センサーのルールでは、スラスター命令そのものを指すアラート（UACE-3 `unauthenticated-tc`）は、**セキュアリンクがオフ**のときに重要な命令が実行された場合だけ出ます。リセット直後はセキュアリンクがオンなので、このルールは出ません。代わりに、**地上局の認証が済む前に**重要な命令が来たことを示すアラート（UACE-6 `command-before-auth`）が出るはずです。センサーは「暗号化されていれば安全」とは見なさず、「誰が送ったかが確かめられていない」ことを問題にしています。
- **地上局モードについて**: このファームには、命令を「地上局の位置から来たもの」に絞る仕組み（地上局モード）があります。ただし初期状態では**オフ**です。この仕組みとその弱点は、段階 4・5 で扱います。
- **現実の例**: 衛星への命令を認証しないと、第三者が衛星を操作できてしまいます。宇宙通信の国際規格（CCSDS）のセキュリティ規格 SDLS では、命令ごとに認証を付ける方式が規定されています。

## 直し方

考えてみてください。

- スラスターの命令は、ファームウェアのどこで処理されていますか？（`Firmware/worker.cpp` の `commandApidHandler` で、`SPP_APID_TC_SET_THRUSTER` の分岐を探す）
- 重要な命令は、**認証済みのセッション**（たとえば、地上局として認証された状態）がないと受け付けないようにする。
- 受け付けた命令にも、受け付けなかった命令にも、**返事を返す**。拒否した理由も返すと、運用者が異常に気付ける。
- 出力の**範囲を確かめ**、ありえない値や存在しない番号は拒否する。
- 直したあと、同じスクリプトを実行し、**スラスターの値が変わらないこと**と、拒否の返事が返ることを、実機で確かめる（スクリプトは、拒否の返事を受け取ると `the board refused:` と表示する）。

## ヒント

1. 命令を受け取ったとき、ファームウェアは「誰が送ったか」を表す情報を、何か調べていますか？
2. `worker.cpp` で、スラスターの命令の分岐を読んでみてください。出力を書き換える前に、何か条件を確かめていますか？ 同じファイルで、命令を拒否している処理（`groundStationCommandAllowed` など）と比べてみてください。
3. スラスターの分岐の先頭で、認証済みのセッションがなければ、エラーを返して処理を終えるようにすると、この攻撃は止まります。出力の上限の確認も、同じ場所に足せます。
