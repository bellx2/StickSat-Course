# ステップ 1: 命令の洗い出し

- **元の攻撃**: `attacks/00_recon_apid_enum/`（演習 1.8）
- **所要時間の目安**: 10〜15 分
- **画面のスコアボード**: `RECON`（状態を問い合わせる命令が届いた時点で点く）

## ねらい

命令の一覧（コマンド辞書）を持っていない状態から、**どんな命令があるかを自分で調べる**。そのとき、衛星の「返事」と「沈黙」から何が読み取れるかを知る。

## 背景

衛星への命令には、種類を表す番号（APID: アプリケーション識別子）が付いています。攻撃者はふつう命令の一覧を持っていません。
では、番号を 1 つずつ変えて命令を送り、返事を記録していくと、何が分かるでしょうか。これが偵察です。この先のすべてのステップはここで作る表から始まります。

## 注意（重要）

- 偵察のスイープ（番号を順に送ること）は、**見つけた命令を実際に実行してしまいます**。スラスターの値やビーコンの間隔なども変わる可能性があります。
- 特に、スイープは副作用として **USB デバッグを有効にします**（番号 `0x10` の `DEBUG_CONFIG`）。有効なままだと、ボードは暗号の処理を飛ばすようになり、いくつか後のステップが原因の分かりにくい形で失敗します。
- **このステップの最後に、必ずリセットしてください。** スイープはスラスター 1 の出力やビーコンの間隔も変えますが、リセット用のスクリプト（`reset_bench.py`）はこれらを戻しません。このステップのあとは、**USB ケーブルの抜き挿し**でリセットするのがおすすめです（[docs/00-start.md](../docs/00-start.md) の方法 2）。
- 番号 `0x02`（`RESETC`）はボードを再起動するため、スクリプトは送りません。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 存在しない番号の命令を送ると、衛星は「そんな命令はない」と返事をすると思う？ 黙ると思う？
- Q2: 返事がなかった番号は、「命令が存在しない」という意味だと思う？
- Q3: 番号を順に送るだけで、センサー（IDS）は攻撃だと気付けると思う？ 1 つ 1 つの命令は形としては正しい。

## 操作

### A. 用意されたスクリプトで試す

1. このステップを始める前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
2. このリポジトリの `attacks/` で、次を実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python 00_recon_apid_enum/00_recon_apid_enum_usb.py

   スクリプトは 2 つのことをする。
   - **誰が話しているか**: 5 秒間、衛星が自分から送ってくるテレメトリを聞き、番号を記録する。
   - **誰が聞いているか**: 番号 `0x01`〜`0x18` に、短い命令を 1 つずつ送り、結果を 3 種類に分ける。
     - `answers`: 同じ番号の返事が来た
     - `rejects`: エラーの返事（番号 `0x09`）が来た
     - `silent`: 何も来なかった
3. 最後に表示される表を、**そのまま保存する**（この先のステップで使う）。

### B. 自分で組み立てる

4. 表の `rejects` の行について、エラーの返事の**中身（文字列）** を確かめたい。スクリプトは中身を表示しない。どこを変えれば表示できるか、自分で読んで変える。ステップ 3 のスクリプトに、エラーの文字列を表示する処理があるので参考にする。
5. 終わったら、**必ずリセットする**（USB ケーブルの抜き挿しがおすすめ）。

## 観察しよう

- 表で、`answers`・`rejects`・`silent` は、それぞれいくつありましたか？
- `0x15` より大きい番号はどれに分類されましたか？ エラーの文字列は何でしたか？
- `silent` になった番号はどれですか？ その番号の命令は本当に存在しないのでしょうか？（ステップ 3 のスラスター命令 `0x04` を思い出してください）
- ボードの画面: スコアボードで `RECON` 以外に点いたものはありますか？ ステータス画面に `DBG` の表示は出ましたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 出たなら、どのルールですか？

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点 1: 存在しない番号に丁寧に返事をする**: この衛星は知らない番号の命令を受け取ると、`Error Unknown APID` というエラーを返します（`Firmware/worker.cpp` の `commandApidHandler` の最後）。存在する命令を中身の誤りで拒否するときは、`GPS OVERRIDE SHORT` や `GS RANGE LOCK` のような**別の文字列**を返します。`rejects` の中でも、エラーの文字列を見れば「存在しない番号」と「存在するが中身が違う命令」を区別できます（B で確かめたこと）。攻撃者から見ると、一覧を教えてもらっているのと同じです。
- **沈黙は「存在しない」ではない**: スラスター命令のように、受け付けても返事を返さない命令があります。この衛星では、`silent` は「黙って実行した」という意味になりえます。エラーが返る番号との**境目**が、命令の一覧そのものです。
- **弱点 2: 調べるだけで状態が変わる**: スイープは見つけた命令を実行します。`DEBUG_CONFIG` を送ると USB デバッグが有効になり、ボードは暗号の処理を飛ばします（`worker.cpp` の `bypass_secure_link`）。調べる側も、調べられる側も、副作用に気付きにくいのが問題です。
- **センサーの見方**: 1 つ 1 つの命令は形としては正しいので、1 件だけでは異常に見えません。センサーは、**存在しない番号への命令が短時間にたくさん来た**ことを手がかりにします（UACE-9 `unknown-apid-rate`）。
- **現実の例**: 機器への攻撃は多くの場合、偵察から始まります。宇宙システムへの攻撃手法をまとめた SPARTA（米国 Aerospace Corporation の枠組み）でも、偵察は最初の段階として整理されています。

## 直し方

考えてみてください。

- 存在しない番号の命令には、**返事をしない**か、存在する命令の拒否と**同じ返事**をする。攻撃者が両者を区別できないようにする。
- `DEBUG_CONFIG` のようなデバッグ用の命令は、運用するファームウェアから**外す**か、認証済みのセッションがないと受け付けないようにする。
- 同じ相手から、存在しない番号への命令が続いたら、しばらく受け付けを止める（レート制限）。
- 直したあと、同じスクリプトを実行し、**表から読み取れる情報が減ったこと**を、実機で確かめる。

## ヒント

1. 存在しない番号を送ったときと、存在する番号を送ったときで、衛星の返事に違いはありますか？
2. `worker.cpp` の `commandApidHandler` の最後の `else` を読んでみてください。知らない番号を受け取ったとき、何をしていますか？
3. 最後の `else` でエラーを返さず捨てるようにすると、存在しない番号は `silent` になり、`Error Unknown APID` という手がかりが消えます。存在する命令の拒否の文字列も、外から区別できない共通のものにすると、表から一覧を読み取りにくくなります。
