# ステップ 4: 取り消しのきかないコマンド

- **元の攻撃**: `attacks/06_resetc/`（演習 2.5）
- **所要時間の目安**: 10〜15 分
- **画面のスコアボード**: なし（再起動すると、スコアボードの記録は消える）

## ねらい

「異常に気付けること」と「被害を止められること」は別だと、実機で体験する。

## 背景

衛星には、フライトコンピュータ（衛星を制御する主コンピュータ）を再起動する命令 `RESETC`（番号 `0x02`）があります。
机の上なら少し待つだけですが、軌道上では事情が違います。衛星と通信できるのは、地上局の上空を通る短い時間（パス）だけです。パスの途中で再起動されると、その回の通信は終わり、次の機会は何時間も先かもしれません。
ステップ 3 のスラスターと同じように、この命令も送り主を確かめないとしたら、どうなるでしょうか。

## 注意

- このステップでは**ボードが再起動します**。USB の接続がいったん切れ、数秒から数十秒で戻ります。
- 再起動すると、画面のスコアボードの記録が消えます。ここまでの記録を残したい場合は、先に画面を写真に撮っておいてください。
- 戻らない場合は、USB ケーブルを抜き、3 秒待って挿し直してください（[docs/00-start.md](../docs/00-start.md) の方法 2）。
- 再起動すると、ボードの状態は起動時の値に戻ります。このステップのあとにリセットは要りません。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 地上局ではない PC から再起動の命令を送ると、衛星は受け付けると思う？
- Q2: 命令を送ってから、ボードがまた返事をするようになるまで、何秒くらいかかると思う？
- Q3: センサー（IDS）はこの命令に気付けると思う？ 気付けたとして、それで再起動を止められると思う？

## 操作

### A. 用意されたスクリプトで試す

1. このステップを始める前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
2. ボードの画面を、システム情報のページ（3 ページ目。BOOT ボタンを短く押すと切り替わる）にし、`RESET`（前回の再起動の理由）と `UPTIME`（起動してからの時間）を**メモする**。
3. このリポジトリの `attacks/` で、次を実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python 06_resetc/06_resetc_usb.py

   スクリプトは `Continue? [y/N]` と確認を求める。**自分の端末で実行し**、`y` を入力する。
   AI に実行させる場合は、ボードが再起動することと、戻らないときの復旧方法（USB の抜き挿し）を確かめてから、`--yes` を付けて確認を省く（付けないと、AI の側で入力待ちのまま止まる）。

4. 出力を、`===` の見出しごとに区切って、上から読む。**次の見出しへ進む前に、その区切りの問いに答える。**

   - `=== 1. uptime before ===`（再起動の前の `STATUS` の返事）
     - 返事は届いたか。この時点では、ボードはふつうに動いている。
     - 次の区切りを読む前に、再起動の命令を送ったら、どんな返事が来るかを予想する。
   - `=== 2. RESETC. No authentication, no acknowledgement, no undo ===`
     - 見出しの英語は「認証なし、受け付けの返事なし、取り消しなし」という意味。命令を送った直後に、返事は来たか。
     - そのあとの `back at T+...s (...s of silence)` の行で、ボードが黙っていた時間は何秒だったか。Q2 の予想と比べる。
     - センサーなしで（`FLATSAT_HOST=1` を外して）実行した場合は、USB の接続が切れて `[+] the link dropped ... -- that is the reboot.` と出ることがある。これは失敗ではなく再起動が起きた印。
5. ボードの画面を見る（システム情報のページでなくなっていたら、もう一度切り替える）。`RESET` と `UPTIME` は手順 2 のメモと比べてどう変わったか。スコアボードはどうなったか。

### B. 自分で組み立てる

6. スクリプトは `STATUS` の返事を 16 進数で表示するだけで、稼働時間（起動してからの秒数）を数字では表示しない。再起動の前と後の稼働時間を、数字で表示するように変えたい。ステップ 10 のスクリプト `01_fuzzing_crash/01_fuzzing_crash_usb.py` に、稼働時間を読む関数 `read_uptime` がある。これを参考に、元のファイルを同じフォルダにコピーしてから（たとえば `my_06.py`）変える。
   `read_uptime` は、返事の先頭から 12 バイト進んだ位置（オフセット 12）にある 4 バイトを「リトルエンディアン」（下位のバイトが先に並ぶ順序）で読んでいる。なぜその位置なのかを、`Firmware/worker.cpp` の `telemetrySPPTransmitMissionStatus`（`STATUS` の返事を組み立てる関数）で、値を詰める順番を数えて確かめる。

## 観察しよう

- ボードの返事: 再起動の命令に、返事はありましたか？ 黙っていた時間は何秒でしたか？
- ボードの画面: `RESET` の理由は何に変わりましたか？ `UPTIME` とスコアボードはどうなりましたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 出たなら、それは**再起動の前**に出ましたか、**後**に出ましたか？
- 稼働時間（B の 6）: 前と後の値は、それぞれいくつでしたか？

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点: 送り主を確かめない、取り消せない命令**: `RESETC` を受け取ると、ファームウェアはすぐに再起動します（`Firmware/worker.cpp` の `commandApidHandler` で `SPP_APID_TC_RESETC` の分岐を探すと、`softwareReset()` を呼んでいるだけです）。地上局モードがオフなら、送り主の確認も、確認の返事もありません。
- **気付けても手遅れ**: この演習のセンサーは命令を見つけても止めずに通す設定（検知だけ）で動いています。センサーが命令を見つけたときには、命令はもう衛星に届いています。再起動は数秒で終わるので、運用者がアラートを読んだ時点では、止める手段がありません。この種類の命令では、検知よりも**受け付けないこと**（予防）のほうが大事です。
- **この演習では元に戻せる**: 元のスクリプトの説明にあるとおり、この演習はあえて「元に戻せる命令」で、検知と手遅れの差を体験します。実際の衛星には取り消しのきかない命令（記憶装置の消去や、機器の電源の遮断など）もあります。
- **再起動を繰り返されると**: 攻撃者が再起動の命令を送り続けると、衛星はパスのたびに通信できなくなります。直すための命令を送ることもできなくなります。
- **ほかのステップとの違い**: ステップ 3 のスラスターはあとから値を戻せました。再起動は、起きた時点で被害（その回の通信を失うこと）が確定します。

## 直し方

考えてみてください。

- `RESETC` のような影響の大きい命令は、**認証済みのセッション**がなければ受け付けない。
- 実行の前に、**2 段階の確認**を求める。たとえば、「再起動の準備」の命令を受けてから、決まった時間内に「実行」の命令が来たときだけ再起動する。
- 受け付けたら、再起動の**前に**返事を返し、記録を残す。
- 短い時間に何度も再起動の命令が来たら、受け付けない。
- 直したあと、同じスクリプトを実行し、**ボードが再起動しないこと**（`UPTIME` が 0 に戻らないこと）を、実機で確かめる。

## ヒント

1. 再起動の命令を受け取ってから、実際に再起動するまでの間に、ファームウェアは何か確かめていますか？
2. `worker.cpp` の `commandApidHandler` で、`SPP_APID_TC_RESETC` の分岐を読んでみてください。何行ありますか？ スラスターの分岐（ステップ 3）と比べて、何が同じですか？
3. 分岐の先頭で、認証済みのセッションがなければエラーを返して終えるようにすると、この攻撃は止まります。さらに「準備」と「実行」の 2 つの命令に分けると、1 つの命令だけでは再起動できなくなります。
