# 段階 5: 地上局のなりすまし

- **元の攻撃**: `attacks/04_gs_auth_spoofing/`（演習 2.4）
- **所要時間の目安**: 20〜30 分
- **前提**: 段階 4（位置を地上局の範囲内にしておく）
- **画面のスコアボード**: `GS AUTH`

## ねらい

弱い認証の仕組みを知り、**弱点が連鎖して突破される**様子を体験する。

## 背景

段階 3 では、誰でもスラスターを動かせました。運用者は、これを防ぐために**地上局モード**を有効にできます。地上局モードが有効だと、重要な命令は、地上局として認証された相手（セッションを持つ相手）からしか受け付けません。
認証は「チャレンジレスポンス」で行います。衛星が問題（チャレンジ）を出し、地上局が正しい答え（レスポンス）を返すと、5 分間のセッションが開きます。
では、この答えの作り方を攻撃者が知っていたら、どうなるでしょうか。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 地上局モードを有効にしたあと、段階 3 と同じスラスターの命令を送ると、どうなると思う？
- Q2: チャレンジレスポンスの「答えの作り方」は、どこに書かれていると思う？ 衛星の中だけ？
- Q3: 段階 4 で位置をごまかさなかったら、この段階の攻撃は成立すると思う？

## 操作

### A. 用意されたスクリプトで試す

1. 段階 4 の続きから始める。位置が札幌（地上局の範囲内）になっていることを、画面で確かめる。リセットした場合は、段階 4 の手順 4 で位置を札幌にする。
2. 運用者の立場で、**地上局モードを有効にする**。このリポジトリの `attacks/` で、次を実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python - <<'PY'
       import sys; sys.path.insert(0, 'lib')
       from flatsat import FlatSat, TC_GS_MODE
       with FlatSat(verbose=False) as f:
           for p in f.send(TC_GS_MODE, b"\x01", seq=1, listen=1.5):
               if p.apid == 0x09:
                   print("ERROR:", f.plaintext(p).split(b"\x00", 1)[0].decode("ascii", "replace"))
       PY

   `ERROR:` が出なければ成功。画面に `GS ON` が出る。
3. 段階 3 のスクリプトで、スラスターの命令を送る。拒否されることを確かめ、`the board refused:` の後ろの理由を**メモする**。

       FLATSAT_HOST=1 uv run python 02_command_injection/02_command_injection_usb.py

4. 地上局になりすまして、セッションを開く。

       FLATSAT_HOST=1 uv run python 04_gs_auth_spoofing/04_gs_auth_spoofing_usb.py

   スクリプトが表示するチャレンジ（`challenge:`）とレスポンス（`response:`）を**メモする**。チャレンジは毎回変わる。
5. 画面の `GS AUTH` 表示と、スコアボードの `GS AUTH` を確かめる。
6. 手順 3 をもう一度実行する。今度はどうなったか。
   セッションは **5 分**で切れる。手順 4 から時間が空いて `GS AUTH REQUIRED` に戻った場合は、手順 4 からやり直す。

### B. 自分で組み立てる

7. 手順 4 でメモしたチャレンジとレスポンスから、「答えの作り方」を自分で確かめる。Python で `hex(チャレンジ ^ レスポンス)` を計算すると、何が出るか。もう一度スクリプトを実行し、別のチャレンジでも同じ値になるか確かめる。
8. JP-Bootcamp の資料は、「ハンドシェイクの途中（チャレンジを受け取ってから答えるまで）に送った命令も通ってしまう」と説明しています。このファームウェアでも本当にそうか、確かめたい。スクリプトには `--inside-window` があり、途中でスラスターの命令を送る。ただし、その命令への拒否の理由は表示しない。拒否の理由を表示するようにスクリプトを変え、結果を確かめる。
9. 終わったら、**リセットする**。地上局モードとセッションが残ったままだと、次の段階が失敗する。リセット用のスクリプトは地上局モードを戻すが、スラスターの出力（手順 6 で 200）は戻さない。0 に戻すなら USB ケーブルを抜き挿しする。

## 観察しよう

- ボードの返事: 手順 3 の拒否の理由は何でしたか？ 段階 4 の拒否の理由（`GS RANGE LOCK`）と比べて、ゲートのどこまで進んだと言えますか？
- チャレンジとレスポンス（B の 7）: `チャレンジ ^ レスポンス` は、毎回同じ値でしたか？
- ボードの画面: `GS ON` と `GS AUTH` は、どの時点で出ましたか？
- `--inside-window`（B の 8）: ハンドシェイクの途中の命令は、受け付けられましたか？ 資料の説明と同じでしたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 出たなら、どの手順で、どのルールですか？

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点 1: 答えの作り方が、共有の定数との XOR**: レスポンスは `チャレンジ XOR 0xC0DEFACE` です（XOR: ビットごとの排他的論理和）。この定数は、衛星のファームウェア（`Firmware/worker.cpp` の `gs_shared_auth_key`）にも、地上局ソフトウェアの設定ファイルにも書かれています。地上局のソフトウェアを手に入れた人は、誰でも答えを作れます。このやり取りが証明しているのは「相手が XOR を計算できること」で、「相手が本物の地上局であること」ではありません。
- **弱点 2: 一度でも答えを見られたら終わり**: XOR は、`チャレンジ XOR レスポンス` で定数そのものが出てきます。通信を 1 回盗み見れば、定数を知らなくても答えを作れるようになります（B の 7 で確かめたこと）。
- **弱点の連鎖**: ゲートは **① GPS の位置 → ② 地上局の範囲 → ③ 認証** の順に確かめます。①②は段階 4 の位置のなりすましで、③は定数との XOR で突破できます。1 つ 1 つの弱点は小さく見えても、**つなげると全部の守りが外れる**のが、この段階の主題です。段階 4 を飛ばすと、②で止まり、チャレンジも出ません（Q3）。
- **資料との違い（`--inside-window`）**: JP-Bootcamp の資料は「チャレンジを出した時点でセッションが開く」と説明しています。このファームウェアでは、チャレンジを出しても、答えが正しいと確かめるまではセッションを開きません（`commandGroundStationAccessHandler`）。B の 8 の結果は、どちらに合いましたか？ 「資料に書いてあること」と「実機で確かめたこと」を分けて記録する練習になります。
- **現実の例**: 機器の認証で、すべての機器に同じ鍵やパスワードを使い、それがソフトウェアの中に書かれている、という問題は、衛星に限らず多くの機器で繰り返し見つかっています。

## 直し方

考えてみてください。

- 共有の定数に頼らない。**機器ごとに異なる秘密の鍵**を持たせ、地上局のソフトウェアに鍵を同梱しない。
- 答えの作り方を、XOR から **HMAC**（鍵付きのハッシュ。答えを見ても鍵が分からない）に変える。`groundStationExpectedResponse` を読んでみる。
- チャレンジは、予測できない乱数で作る。今の `groundStationGenerateChallenge` は、起動からの時間と位置から作っている。
- 認証の失敗が続いたら、しばらく受け付けを止める。
- 位置の確認と認証を、**独立に**行う。位置をごまかしても、認証が弱くても、片方だけでは突破できないようにする。
- 直したあと、同じスクリプトを実行し、**セッションが開かないこと**と、スラスターの命令が拒否されることを、実機で確かめる。
