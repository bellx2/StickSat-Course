# ステップ 10: 長さの引き算で落ちる

- **元の攻撃**: `attacks/01_fuzzing_crash/`（演習 2.1）
- **所要時間の目安**: 20〜30 分
- **画面のスコアボード**: なし（ボードが落ちて再起動すると、スコアボードの記録は消える）

## ねらい

C 言語の「符号なし整数の引き算」が一周する（アンダーフロー）と何が起きるかを、コードを読んで予想し、実機で確かめる。

## 背景

この衛星には、受け取ったメッセージを地上へ中継する命令 `BROADCAST_MSG` があります。中身の先頭 2 バイトは周波数で、残りがメッセージです。
ファームウェアは「中身の長さ − 2」でメッセージの長さを計算します。では、中身が 2 バイトより短かったら、この引き算はどうなるでしょうか。

## 注意

- このステップでは、**ボードをわざと落とします**（クラッシュ）。ボードは再起動するか、画面が固まったまま止まります。
- 画面が固まったまま 30 秒たっても戻らない場合は、USB ケーブルを抜き、3 秒待って挿し直してください（[docs/00-start.md](../docs/00-start.md) の方法 2）。
- 再起動すると、ボードの状態は起動時の値に戻り、画面のスコアボードの記録も消えます。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 中身が 1 バイトのとき、「中身の長さ − 2」はいくつになると思う？ 長さを表す型が負の数を表せない型（`size_t`）だとしたら？
- Q2: その長さでメモリをコピーしようとしたら、何が起きると思う？
- Q3: センサー（IDS）はこの命令を「おかしな長さ」として見分けられると思う？

## 操作

### A. コードを読んで予想する

1. `Firmware/worker.cpp` の `commandApidHandler` で、`SPP_APID_TC_BROADCAST_MSG` の分岐を探し、次の 3 行を読む。

       size_t payload_total = space_packet->header.length + 1;
       size_t msg_len = payload_total - 2;
       memcpy(buffer_msg, space_packet->data + 2, msg_len);

   - `memcpy` は、指定した長さのバイトを、別の場所（`buffer_msg`）へコピーする関数。`buffer_msg` は何バイトの大きさか（`SPP_MAX_PAYLOAD_CHUNK`、`Firmware/spp.h` で定義）。
   - `header.length` は「中身の長さ − 1」を入れる決まり（宇宙通信のパケットの規格 CCSDS の決まり）。なぜ「− 1」なのか、長さ 0 をどう表すかを考える。
2. 符号なしの引き算を、Python で真似る。`size_t` は、このボードでは 32 ビット（0〜約 42.9 億）。

       uv run python -c "print((1 - 2) % 2**32)"

   出た数を、`buffer_msg` の大きさと比べる。Q1・Q2 の答えを書き直したくなったら、書き直してよい。

### B. 用意されたスクリプトで確かめる

3. このステップを始める前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
4. ボードの画面を、システム情報のページ（3 ページ目。BOOT ボタンを短く押すと切り替わる）にし、`RESET` と `UPTIME` を**メモする**。
5. このリポジトリの `attacks/` で、次を実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python 01_fuzzing_crash/01_fuzzing_crash_usb.py

   スクリプトは、中身が空になる `BROADCAST_MSG` を 1 回だけ送り、そのあと稼働時間（起動してからの秒数）が 0 に戻ったかで、落ちたかどうかを判定する。
6. 出力を、上から順に読む。

   - `[*] uptime before: ... s` の行（送る前の稼働時間）
   - `=== did it reboot? ===` のあとの行
     - `[+] uptime ... s -> ... s.` と出たら、稼働時間が戻った（落ちて再起動した）。
     - `[*] could not read the uptime on both sides.` と出たら、スクリプトは判定できなかった。ボードの画面で確かめる。
   - センサーなしで（`FLATSAT_HOST=1` を外して）実行した場合は、送った直後に USB の接続が切れ、`[+] the link died during the send` と出て終わることがある。そのときは `=== did it reboot? ===` は出ないので、ボードの画面で確かめる。
7. ボードの画面を見る（システム情報のページでなくなっていたら、もう一度切り替える）。画面は固まったか、再起動したか。`RESET` と `UPTIME` は手順 4 のメモと比べてどう変わったか。

### C. 自分で組み立てる

8. スクリプトの `--sweep` は、中身の長さを 12 バイトから 0 バイトまで 1 つずつ減らしながら送る（`=== walking the declared length down ===`）。**何バイトのときに落ちるか**を、A のコードから先に予想して書く。そのあと、リセットしてから `--sweep` を付けて実行し、`declared ...` の行がどこで止まったかで確かめる。
   落ちる前の長さでは、`[!] the board refused: BROADCAST RADIO DISABLED` が並ぶ。これはゲートの拒否ではなく「命令は受け付けて処理したが、このボードには無線がないので送信しなかった」という返事。
   ヒント: 暗号化された命令は、ボードで復号されたあとの長さで `header.length` が決まる（`secureLinkDecodeInPlace` の終わり近くで `header.length` を設定している行）。

## 観察しよう

- ボードの返事: 命令を送ったあと、ボードは返事をしましたか？
- ボードの画面: 固まりましたか、再起動しましたか？ `RESET` の理由はステップ 4 の `RESETC` のときと同じでしたか？
- `--sweep`（C の 8）: 何バイトのときに落ちましたか？ 予想と合いましたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 出なかったなら、センサーに見えていた長さは何バイトだったと思いますか？

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点: 引き算の前に長さを確かめていない**: `payload_total` が 2 より小さいと、`payload_total - 2` は負の数にならず、一周して約 42.9 億になります。これを「整数のアンダーフロー」と呼びます。`size_t` は負の数を表せない型だからです。その巨大な長さのまま `memcpy` が動き、200 バイトしかない `buffer_msg` の外側のメモリを次々に書き換えます。CPU は続けられない異常（ハードフォールト）に陥ります。
- **長さ 0 と 1 が同じになる**: パケットの `header.length` は「長さ − 1」なので、中身が 0 バイトのときも、ファームウェアは `header.length` を 0 にします（`secureLinkDecodeInPlace` の終わり近くで `header.length` を設定している行）。0 バイトでも 1 バイトでも、`payload_total` は 1 になり、引き算が一周します。
- **周波数の読み出しも危ない**: 同じ分岐の先頭で、中身の先頭 2 バイトを周波数として読んでいます。中身が 2 バイトより短いと、届いていないバイトを読んでいることになります。
- **センサーの見方**: センサーには、`BROADCAST_MSG` の長さが短すぎることを検知するルール（UACE-8 `length-underflow`）があります。ただし、センサーが見る長さは、暗号化されたあとのパケットの長さです。暗号化すると中身は 16 バイト単位に詰められるので、B の手順 5 で送った「復号すると空になる命令」も、外から見ると 16 バイトあります。
- **現実の例**: 長さの計算の誤りから、決められた大きさを超えてメモリに書き込んでしまう不具合（バッファオーバーフロー）は、衛星に限らず、通信を受け取るソフトウェアで繰り返し見つかっている弱点です。外から届いた長さは、**使う前に必ず確かめる**のが基本です。

## 直し方

考えてみてください。

- 引き算の**前に**、`payload_total` が 2 以上であることを確かめる。足りなければ、エラーを返して処理を終える。
- コピーする長さが `buffer_msg` の大きさ（`SPP_MAX_PAYLOAD_CHUNK`）を超えないことも確かめる。
- 周波数を読む前にも、中身が 2 バイト以上あることを確かめる。
- 直したあと、同じスクリプト（`--sweep` も）を実行し、**ボードが落ちないこと**（`UPTIME` が 0 に戻らないこと）と、エラーの返事が返ることを、実機で確かめる。

## ヒント

1. `payload_total` が 1 のとき、`msg_len` はいくつになりますか？ 型が `size_t` であることに注意してください。
2. `memcpy` でコピーする先の `buffer_msg` は何バイトですか？ `msg_len` がそれより大きいとき、`memcpy` を止める処理はありますか？
3. `size_t msg_len = payload_total - 2;` の前に、`if (payload_total < 2) { telemetrySPPTransmitError("BROADCAST TOO SHORT"); return; }` のような確認を足すと、この攻撃は止まります。
