# 段階 2: リプレイ

- **元の攻撃**: `attacks/05_replay/`（演習 1.10）
- **所要時間の目安**: 15〜20 分
- **画面のスコアボード**: 専用のマイルストーンはなし。ステータス画面の `LAST CMD` の `n=`（受け付けた命令の数）の変化を見る

## ねらい

「暗号化されている」ことと、「安全に通信できている」ことは別だと、実機で体験する。

## 背景

この衛星への命令（テレコマンド）は、セキュアリンクで暗号化されています。
暗号化された命令は、中身を読めません。では、**一度記録した命令を、そのままもう一度送ったら**どうなるでしょうか。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 暗号化された命令を、そのまま再送すると、衛星は受け付ける？ 拒否する？
- Q2: 受け付けるとしたら、何回でも？ それはなぜ問題になる？
- Q3: 拒否する仕組みを作るなら、命令に何を足せばいい？

## 操作

この段階では、スラスター（衛星の向きや軌道を変える小さな噴射装置）の出力を変える命令を使います。スラスターの命令そのものは段階 3 で詳しく扱います。ここでは「記録した命令の例」として使うだけです。

1. 段階の前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
2. このリポジトリの `attacks/` で、次を実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python 05_replay/05_replay_usb.py

   スクリプトは次の順に進む。
   - 運用者が送る命令（スラスター 0 の出力を 128 にする）を暗号化し、**記録**として保存する。ここから先、鍵は使わない。
   - 変更前の状態を読む。
   - 記録をそのまま送る（1 回目）。
   - スラスターを手で 0 に戻す。2 回目の効果を見分けるため。
   - **同じバイト列**をもう一度送り、状態を読む。
   - さらに同じバイト列を 10 回送り、状態を読む。
3. 回数を変えて試す（`--times 3` など）。
4. 終わると、スラスターの出力が 128 のまま残る。リセット用のスクリプト（`reset_bench.py`）はスラスターを戻さない。段階 3 に続けて進むなら、そのままでよい（段階 3 は変更前の値を読んでから始める）。0 に戻したいときは、USB ケーブルを抜き挿しする（[docs/00-start.md](../docs/00-start.md) の方法 2）。

## 観察しよう

- 0 に戻したあとの再送で、スラスターの出力はもう一度 128 になりましたか？
- ボードの画面の `LAST CMD` の `n=` は、何回分増えましたか？ スクリプトが送った命令（状態の問い合わせも含む）の数と一致しましたか？
- スクリプトは最初に、記録した命令のバイト列（16 進数）を表示します。再送のとき、スクリプトはこのバイト列を作り直していますか？（スクリプトの `send_raw` の行を読んでみる）
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 出たなら、どのルールで、何を根拠にしていますか？

予想（Q1・Q2）と、どこが違いましたか？

## 解説

- **弱点**: 暗号は、命令の**中身を隠す**ものです。命令が**新しい**ことは保証しません。
- **この衛星の暗号**: ファームウェアに書かれた固定の鍵で、AES という暗号を使っています。改ざんを見分ける仕組み（MAC: メッセージ認証コード）はありません。そのため、暗号は「誰が送ったか」も保証しません。この点は段階 3 で扱います。
- **同じ命令は、毎回同じバイト列になる**: この暗号の使い方（ECB という方式）では、同じ命令を暗号化すると、毎回まったく同じ暗号文になります。受け取る側には、正規の 2 回目の命令と、記録した命令の再送を区別する手がかりがありません。
- **連番はあるが、見ていない**: 命令の見出し部分（SPP ヘッダ）には、14 ビットの連番の欄があります。ボードはこの値をログに出しますが、受け付けの判断には使っていません。しかも見出し部分は暗号化されないので、攻撃者が書き換えることもできます。
- **センサーは気付く**: センサーには、同じ連番のフレームが繰り返し届いたことを検知するルール（UACE-7 `duplicate-frame`）があります。センサーは気付けるのに、衛星は同じ情報を見ずに命令を実行しています。
- **元の資料との違い**: JP-Bootcamp のスクリプトのコメントは、「暗号は、鍵を持つ者が送ったことを証明する」という立場です。このカードでは、鍵がファームウェアに固定で書かれ、公開されたソースから誰でも読めるので、送り主の証明にはならない、と説明しています。
- **現実の例**: 鍵付きの車や、ドアの開閉などでも、記録した信号の再送が問題になります。宇宙通信の国際規格（CCSDS）のセキュリティ規格 SDLS では、再送を防ぐための連番（Anti-Replay Sequence Number）が規定されています。

## 直し方

考えてみてください。

- 命令に**連番（カウンター）**か**時刻**を入れ、受け取る側が「前より新しいか」を確かめる。
- 連番は、攻撃者が書き換えられない場所に入れる。暗号化されない見出し部分では、書き換えられてしまう。連番を含めた命令全体に **MAC**（鍵を持つ人だけが作れる検査値）を付け、受け取る側で確かめる。
- ファームウェアのどこで、命令の受け付けを判断していますか？（`Firmware/worker.cpp` の `commandHandlerInternal` を読んでみる。復号、地上局ゲート、命令の実行の順に進む）
- 直したあと、**同じ再送が拒否されること**を、実機で確かめる。

## ヒント

1. 再送した命令と、最初に送った命令は、バイト列として**同じ**ですか？ 受け取る側は、それを区別できますか？
2. 命令の見出し部分に、「今回が何回目か」を表す欄はありますか？ あるなら、受け取る側はその値を確かめていますか？ 攻撃者はその値を変えられますか？
3. 受け取る側が、最後に受け付けた連番を覚えておき、それ以下の連番を拒否すると、再送は止まります。連番は暗号化または MAC で守られた部分に入れないと、攻撃者が書き換えて通してしまいます。
