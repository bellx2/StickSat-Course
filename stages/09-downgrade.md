# ステップ 9: 暗号のダウングレード

- **元の攻撃**: `attacks/07_secure_link_downgrade/`（演習 2.6）
- **所要時間の目安**: 15〜20 分
- **画面のスコアボード**: `AES CFG`（命令が届いた時点で点く。StickSat v1.2.1 以降。暗号が実際に切れたかは `STATUS` の返事で確かめる）

## ねらい

暗号を**使っている**ことと、暗号が**切られない**ことは別だと、実機で体験する。

## 背景

この衛星の通信はセキュアリンク（AES という暗号）で守られています。ここまでのステップでは、攻撃側のスクリプトも同じ鍵で暗号化して命令を送っていました。
ところで、衛星には「セキュアリンクを使うかどうか」を切り替える命令（`AES_CONFIG`、番号 `0x0A`）があります。この切り替えの命令そのものはどう守られているでしょうか。

## 注意

- 暗号をオフにしたあとは、**暗号化されていない命令**（`--cleartext`）でないと通らなくなります。
- 終了時に `--restore` を付けると、暗号をオンに戻せます。**必ず戻すか、リセットしてから**次へ進んでください。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 暗号をオフにする命令は何バイトくらいの大きさだと思う？
- Q2: 暗号をオフにする命令を送るのに、暗号の鍵は必要だと思う？
- Q3: 暗号がオフになった瞬間を、センサー（IDS）は見分けられると思う？ オフになったあとの通信はどう見えると思う？

## 操作

### A. 用意されたスクリプトで試す

1. このステップを始める前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
2. このリポジトリの `attacks/` で、次を実行する（センサー経由）。

       FLATSAT_HOST=1 uv run python 07_secure_link_downgrade/07_secure_link_downgrade_usb.py

3. 出力を、`===` の見出しごとに区切って、上から読む。**次の見出しへ進む前に、その区切りの問いに答える。**
   スクリプトは一気に最後まで動くので、画面を上へ戻して、見出し 1 つ分ずつ読むとよい。

   - `=== 1. before ...`（変更前の `STATUS` の返事）
     - `[=] payload looks ...` の行を読む**前に**、16 進数の表示の右側（読める文字の欄）を見て、読める内容かどうかを自分で判断する。判断してから `[=]` の行と見比べる。
   - `=== 2. the entire exploit ...`（`AES_CONFIG` に `00` を送る）
     - 送った命令の中身は何バイトだったか。Q1 の予想と比べる。
     - 次の区切りを読む前に、変更後の返事がどう見えるかを予想する。
   - `=== 3. after ...`（変更後の `STATUS` の返事）
     - 1 と同じように、`[=]` の行より先に自分で判断する。1 と比べて、右側の欄はどう変わったか。
     - 最後の `secure link flag:` の行は、暗号の設定が前後でどう変わったと言っているか。
   - `=== 4. putting it back ===` は、`--restore` を付けたときだけ出る。
4. ボードの画面を見る。`LAST CMD` に `AES_CFG` が出たか。スコアボードの `AES CFG` は点いたか。暗号が今オンかオフかを示す表示はあるか。

### B. 自分で組み立てる

5. スクリプトは暗号をオフにする命令を、**鍵を使って暗号化して**送っている。では、鍵を知らない攻撃者が、**暗号化しないまま** `AES_CONFIG` に `00` を送ったらどうなるか。リセットしてから、スクリプトの該当行を変えて確かめる（`fsat.send` には `encrypt=False` を渡せる）。
6. 終わったら、`--restore` を付けて実行するか、リセットする。

## 観察しよう

- 変更前と変更後の `STATUS` の返事: どちらが読めるバイト列でしたか？ スクリプトの最後の判定（`secure link flag:` の行）は、どうなりましたか？
- 鍵なしの命令（B）: 暗号化しない `00` は受け付けられましたか？
- ボードの画面: スコアボードの `AES CFG` はどの時点で点きましたか？ 画面から、暗号が今オフになっていると分かりましたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 出たなら、どのルールで、何を根拠にしていますか？

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点 1: 暗号の切り替えがふつうの命令**: 暗号をオフにするのは、1 バイトの `00` を載せた命令 1 つだけです（`Firmware/worker.cpp` の `commandAesConfigHandler`）。暗号そのもの（AES）は破られていません。鍵も解読していません。**暗号を使わせない**ほうが、暗号を破るよりずっと安上がりです。これを「ダウングレード攻撃」と呼びます。
- **弱点 2: 暗号化されていない命令でも受け付ける**: `AES_CONFIG` の中身を読む処理（`extractToggleConfigMode`）は、まず復号を試し、うまくいかなければ**暗号化されていない 1 バイト目をそのまま使います**。つまり、鍵を知らなくても暗号をオフにできます（B で確かめたこと）。暗号を守るはずの設定が、暗号の外に置かれています。
- **状態が見えない**: ボードの画面には暗号が今オンかオフかの表示がありません。`AES CFG` は「命令が届いた」ことを示すだけで、オンにする命令でも点きます。暗号がオフになったことは、`STATUS` の返事の中の印（セキュアリンクのフラグ）を読まないと分かりません。運用者が気付きにくいことも、弱点の一部です。
- **認証もない**: 地上局モードがオフなら、衛星はこの命令についても、ステップ 3 のスラスターと同じく送り主を確かめません。
- **センサーの見方**: センサーには、セキュアリンクの印が「直前のフレームではオン、このフレームではオフ」になった**切り替わりの瞬間**を検知するルール（PWN-4 `secure-link-downgrade`）があります。切り替わったあとは、平文（暗号化されていないデータ）の通信がふつうに流れるだけなので、**後から見ると正常に見えます**。
- **元のスクリプトの注意点**: JP-Bootcamp の資料に、このスクリプトの `secure link flag:` の判定は、変更前の値を暗号文のまま読んでいるため、当たるかどうか五分五分だという記載があります（`docs/04-attacks.md` の「キット自体の2つの欠陥」）。判定よりも、**読めないバイト列が読めるようになった**という見比べのほうを信じてください。
- **現実の例**: JP-Bootcamp のスクリプトは、この攻撃を、宇宙通信のセキュリティ規格 SDLS を実装したソフトウェア（CryptoLib）でのダウングレードの類例として挙げています。一般に、通信の保護を「使わない」側へ誘導するダウングレード攻撃は、Web の暗号通信（TLS）などでも繰り返し問題になってきました。暗号の強さ（鍵の長さなど）をいくら上げても、この形の攻撃は防げません。

## 直し方

考えてみてください。

- 暗号の設定を変える命令は、**暗号化され、認証された命令**でしか受け付けない。暗号化されていない命令で暗号をオフにできないようにする（`extractToggleConfigMode` の最後の行）。
- 暗号をオフにする操作そのものを、運用中は受け付けない。どうしても必要なら、地上局として認証されたセッションと、二重の確認を必須にする。
- 暗号の状態が変わったら、地上局に必ず知らせ、記録を残す。
- 直したあと、同じスクリプト（B の、暗号化しない版も）を実行し、**セキュアリンクがオンのまま変わらないこと**を、実機で確かめる。

## ヒント

1. 暗号をオフにする命令が、ほかの命令（たとえばスラスター）より強く守られているか、比べてみてください。
2. `worker.cpp` の `extractToggleConfigMode` を読んでみてください。復号に失敗したとき、何をしていますか？
3. 復号に失敗したら、`false` を返して命令を拒否するように変えると、鍵なしでのダウングレードは止まります。さらに、`commandAesConfigHandler` の前に、認証済みのセッションを必須にする確認を足すと、鍵を持つ攻撃者も止められます。
