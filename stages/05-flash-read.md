# ステップ 5: フラッシュの読み出し

- **元の攻撃**: `attacks/08_flash_read_dump/`（演習 2.7）
- **所要時間の目安**: 15〜20 分
- **画面のスコアボード**: `FLASH RD`（読み出しの命令が届いた時点で点く）

## ねらい

誰にでも配られている値は「鍵」にならないことと、衛星の中に置いた秘密は読み出されうることを、実機で体験する。

## 背景

この衛星には、フラッシュメモリ（電源を切っても消えない記憶領域）の一部を保守のために地上から読み出す命令 `FLASH_READ` があります。
読み出しには 2 つの値（窓の番号と、解除のための値）を正しく指定する必要があります。いわば、読み出しの扉にかかった錠です。
ただし、この 2 つの値は地上局のソフトウェアの設定ファイルにも書かれています。地上局のソフトウェアを手に入れた人なら、誰でも知っている値です。

## 予想してみよう

実行する**前**に、考えて書いてください。

- Q1: 地上局のソフトウェアに書かれた 2 つの値を使えば、読み出しの扉は開くと思う？
- Q2: 読み出したメモリに、どんなものが入っていると思う？ 攻撃者にとって一番価値があるのは何だと思う？
- Q3: 読み出しを 1 回だけ行うのと、何回も続けて行うのとで、センサー（IDS）の見え方は変わると思う？

## 操作

### A. 用意されたスクリプトで試す

1. このステップを始める前に、ボードをリセットする（[docs/00-start.md](../docs/00-start.md)）。
   ステップ 1（命令の洗い出し）のあとにリセットしていないと、USB デバッグがオンのまま残り、正しい値でも `FLASH WINDOW LOCKED` と拒否される。
2. このリポジトリの `attacks/` で、次を実行する（センサー経由）。読み出した中身を `flash.bin` というファイルに保存する。

       FLATSAT_HOST=1 uv run python 08_flash_read_dump/08_flash_read_dump_usb.py --out flash.bin

3. 出力を、`===` の見出しごとに区切って、上から読む。**次の見出しへ進む前に、その区切りの問いに答える。**

   - 先頭の `[*] window=0x.. unlock=0x....` の行
     - スクリプトが使う 2 つの値は何か。どこから持ってきた値だと書いてあるか。
   - `=== 1. one window, to see whether the gate opens at all ===`
     - 扉は開いたか（`FLASH WINDOW LOCKED` と出たら開いていない）。
     - 16 進数の表示の右側（読める文字の欄）に、何が見えるか。
     - 次の区切りを読む前に、メモリの続きに何が入っていそうかを予想する。
   - `=== 2. walking 0x0000..0x0400 ===`
     - 1 回の読み出しで、何バイトずつ進んだか（`0x0000+32` のような表示）。スクリプトは 64 バイトずつ頼んでいる。
     - `past the end of the window` の行は何バイト目で出たか。読み出せる範囲は、どれくらいの大きさだったか。
   - 最後の `Next: run the key-recovery method from lab 2.1 ...` の行は JP-Bootcamp の講座の案内なので、この演習では読み飛ばしてよい。
4. 保存したファイルを、読める文字として表示する。

       uv run python -c "print(open('flash.bin', 'rb').read().decode('ascii', 'replace'))"

   1 行ずつ読み、それぞれの行が何を表していそうかを考える。**16 文字の、鍵のように見える行**はあるか。
5. ボードの画面を見る。スコアボードの `FLASH RD` は点いたか。

### B. 自分で組み立てる

6. 手順 4 で見つけた鍵のような 16 文字が、本当に衛星の暗号の鍵かを確かめる。`Firmware/secure_link.cpp` で `secure_link_key` を探し、1 文字ずつ見比べる。
7. 読み出しの命令の中身は 6 バイトで、2 つの値は**違う並び順**で詰められている（スクリプトの先頭の説明と、`read_request` 関数を読む）。解除のための値 `0xC35A` を、間違えて逆の順序で詰めたら扉は開くか。`--unlock 0x5AC3` を付けて実行し、確かめる。結果を見る前に、予想を書く。
8. 窓の番号を 1 つずらした `--window 0xA4` でも試す。拒否の理由は手順 7 と同じだったか。

## 観察しよう

- ボードの返事: 扉は開きましたか？ 間違った値（B の 7・8）では、どんな理由で拒否されましたか？
- 読み出した中身: 鍵のほかに、何が入っていましたか？ 扉を開けるための 2 つの値そのものも、中に書かれていませんでしたか？
- ボードの画面: `FLASH RD` はどの時点で点きましたか？
- センサー（IDS）のコンソール（http://127.0.0.1:5011）に、アラートは出ましたか？ 出たなら、どのルールで、読み出しの何回目あたりで出ましたか？

予想（Q1〜Q3）と、どこが違いましたか？

## 解説

- **弱点 1: 錠の値が、配られたソフトウェアに入っている**: 扉を開ける 2 つの値はファームウェアの中の固定の値です（`Firmware/worker.cpp` の `flash_window_id` と `flash_unlock_tag`）。同じ値が地上局ソフトウェアの設定ファイルにも書かれています。全員に配られる値は秘密ではありません。知らない人を足止めするだけの「障害物」です。
- **弱点 2: 秘密を、読み出せる場所に置いている**: 読み出せる領域（`flash_window_blob`）には、運用の設定と並んで、セキュアリンクの鍵と同じ 16 文字が入っています（B の 6 で確かめたこと）。鍵を手に入れれば、ステップ 2・3 で攻撃側のスクリプトが使ったのと同じ鍵で、命令を暗号化できます。ここまでのステップでは「鍵はソースコードに書かれている」から使えましたが、このステップでは**衛星そのものから**鍵を取り出しました。
- **エンディアン**: 同じ 6 バイトの中で、読み出す位置（オフセット）は下位のバイトが先（リトルエンディアン）、解除のための値は上位のバイトが先（ビッグエンディアン）で詰められています（`commandApidHandler` の `SPP_APID_TC_FLASH_READ` の分岐）。並び順を 1 つ間違えると、値が正しくても扉は開きません（B の 7）。通信の仕様を読むときは、各値の並び順を必ず確かめます。
- **1 回の読み出しの上限**: ボードは 1 回に 32 バイトまでしか返しません（`flash_read_max_bytes`）。それでも、位置をずらしながら何度も読めば、領域全体を写し取れます。上限は読み出しを遅くするだけです。
- **センサーの見方**: センサーには、短い間に何回も読み出しが続くことを検知するルール（PWN-5 `flash-read-sweep`）があります。1 回の読み出しは保守かもしれませんが、位置をずらしながら続く読み出しは、誰かが中身を写し取っている可能性が高い、という考え方です。

## 直し方

考えてみてください。

- 読み出しは、固定の値ではなく**認証済みのセッション**がある場合だけ受け付ける。
- 鍵などの秘密を、地上から読み出せる領域に置かない。読み出せる範囲を、本当に必要な設定だけに絞る。
- 機器ごとに違う鍵を使う。1 台から鍵が漏れても、ほかの衛星は守られるようにする。
- 短い間に続く読み出しを受け付けない。または、読み出しのたびに記録を残し、地上に知らせる。
- 直したあと、同じスクリプトを実行し、**扉が開かないこと**（または、鍵が読み出した中身に含まれないこと）を、実機で確かめる。

## ヒント

1. 読み出しの扉を開けるのに必要なものは、衛星と地上局のほかに、どこにありますか？ 読み出した中身もよく見てください。
2. `worker.cpp` で `flash_window_blob` を探し、中に何が書かれているかを読んでみてください。それを `secure_link.cpp` の `secure_link_key` と比べてみてください。
3. `commandApidHandler` の `SPP_APID_TC_FLASH_READ` の分岐で、2 つの値を比べる代わりに、認証済みのセッションがあるかを確かめるようにすると、この攻撃は止まります。あわせて、`flash_window_blob` から鍵の行を取り除くと、扉が開いても鍵は漏れません。
